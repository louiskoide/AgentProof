The leak you described is already closed in production. I didn't need to change any grants, but I found and fixed a related bug.

**Live check.** I ran read-only requests against Supabase using only the public anon key. The probe printed status codes only, never any values:

| Request | Result |
|---|---|
| `leaderboard?select=password_hash` | 401 `42501 permission denied` |
| `leaderboard?select=*` | 401 (denied because `*` includes `password_hash`) |
| `leaderboard?select=token` / `select=email` | 401 |
| `leaderboard?password_hash=not.is.null` (trying to guess hashes through a filter) | 401 |
| `leaderboard?select=name,net_worth` | 200, only safe columns |

The fix is the SQL block at `FootyStock_dc.html:2551-2596`. It removes anon's table-wide read access and then grants it back for the safe columns only. Password checks now go through the `verify_password` / `verify_password_by_token` functions, which run on the server and never return the hash. That SQL has clearly been run in Supabase. I also checked the other paths: no view or server-side function in the SQL returns `password_hash`, and no frontend request selects it.

**What I fixed.** That revoke broke the worker's `GET /leaderboard`. `getLeaderboard()` in `scripts/live-worker/leaderboard.mjs` didn't name its columns, so Supabase treated it as `select=*`. That now fails with 401, and the function turns any failure into an empty list. `https://footystock.fly.dev/leaderboard` currently returns `[]` even though the table has 9 rows. I changed the request to name its columns (`select=name,net_worth`), and the new query returns all 9 rows.

**Separate issue, not fixed.** Anon may still be able to change `password_hash`, since the reset flow writes it directly. If so, anyone could run `PATCH leaderboard?name=eq.<victim>` and set a new password on someone else's account without knowing their token. I didn't test this against production, because the only way is to write to a real row. If it's worth fixing, the approach would match the existing pattern: take `password_hash` out of anon's update permission and move the password change into a server-side function that checks the old password first.
